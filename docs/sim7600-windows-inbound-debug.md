## 2. 问题时间线（按根因，不是按心情）

### 2.1 音色不受支持 → 开场白 `response.create` 直接失败

**现象**：来电接通后电话静音。  
**日志**：

```text
Unsupported voice: 'Raymond'.
Supported voices: longanqian, longanlingxin, …, loongmary, …
Cannot create response: conversation has no messages or no user message.
```

**原因**：

1. 旧默认 / UI choices 仍含 `Raymond` 等 Omni 旧音色；`qwen-audio-3.0-realtime-*` 不认。
2. 即便音色修好，`say()` 只调 `create_response(instructions=…)`，**空会话无 user message** 时新模型拒绝开场。

**修复**：

- `.env` / 默认：`QWEN_VOICE=longanqian`（后为听感改为 `loongmary`）；`config.py` choices 同步为新列表。
- [`qwen_agent.py`](../src/agentcall/agents/qwen_agent.py) `say()`：先 `create_item(role=user, input_text=instructions)`，再 `create_response`（同 MiniMax 约束一类）。

**证据通话**：`20260810-175332-inbound-*`（失败）、其后音色修复通仍可能踩「无 user message」。

### 2.2 开场白已生成，但 COM6 写超时 → 电话仍静音

**现象**：日志有 `[下行·Agent] 喂您好…`，对方仍无声。  
**日志特征**：

```text
写入 NMEA PCM 超时，丢弃本帧继续 (累计 N 次)
agent_queued=0 或写统计几乎无成功 written
```

**对照成功通**（`20260810-181124` / `20260810-182131`）：

```text
written≈80000 bytes / 5s, agent_queued>0
```

**根因要点**：

| 写法 | 结果（本机真机） |
|---|---|
| `write_timeout=0.15`（为「保节拍」误改） | **整通写失败 → 静音** |
| `write_timeout=1.0`（Windows Audio COM） | **可写、可闻** |
| macOS libusb 同步 bulk OUT | 见 `HANDOVER.md`，与本路径不同 |

**修复**：[`audio_bridge.py`](../src/agentcall/audio_bridge.py) `_write_timeout_seconds`：PTY `0.2s`，非 PTY（Windows COM）`1.0s`。  
另：`simcom_pcm` 在 `AT+CPCMREG` **之前** `preclaim()` 打开 Audio 口（官方示例时序）。

**教训**：Windows 虚拟 COM 上「写超时过短」会表现为**完全无声**，不是「略卡」；调节拍前先看 `written` / `agent_queued`。

### 2.4 听感：偏大 / 断续 / 「隔着木板」

**量化（`downlink.wav`，8k mono）**：

| 通话 | tx_gain | speech RMS | peak | high/mid* | 听感 |
|---|---|---|---|---|---|
| `181124` | 1.0（无软限） | ~4473 | ~18k | ~0.097 | 偏轻、闷 |
| `182131` | 2.5 + 全程 tanh 软限 | ~10k | ~24k | ~0.16 | **过大**、糊 |
| `182906` | 1.5 + 软限 | ~8351 | ~24k | ~0.17 | 仍偏大、闷 |
| `183256` | 1.2 + 轻预加重 | ~5171 | ~27k | ~0.143 | 仍闷；句中近静音缝约 1s |
| （目标）现行链路 | 1.35 + HP/预加重 + preroll | — | — | 目标 ≥0.22 | 待主观确认 |

\*high/mid：语音帧上 2–3.4kHz 能量 / 0.3–1kHz 能量中位数。

**2026-08-10 晚续（断续 + 仍闷 → 一度静音）**：

1. **Windows SimTech Audio COM 必须用 `MODEM_PCM_BAUD=115200`**（与可闻通话一致）。改成 `921600` 后通话 `184509`：**有 Agent 开场白转写，但零成功写统计 → 电话静音**。  
   教训：`.env.example` 默认 921600 是给 macOS PTY/Quectel 路径的；**不要**在本机 Windows Audio COM 上照抄。  
2. **写超时「回队重试、不 flush」在全程超时场景会写死**：背压下越积越多，整通无声。已回退为 **丢帧 + `reset_output_buffer`**（可闻优先）。  
3. **preroll 默认关闭**（可选逻辑保留）。  
4. **清晰度**：保留「~180Hz 高通去泥 + 更强预加重」；`MODEM_TX_GAIN=1.35`。  
5. **venv→系统 Python 父子进程**属正常；两个无关 `app.py` 才抢口。  
6. **`CPCMREG mode 1` 失败（Call setup failed）**：通话 `184908` 在错误波特率静音通之后出现——`AT+CPCMREG=1` 连试 3 次读不回 mode=1，软件会 `AT+CRESET` 并提示彻底断电 10s。这是模组 USB Audio 端点卡死，不是仪表盘文案问题；恢复顺序：停 Edge → 拔电/关电源 10s → 上电等 COM 齐 → 确认 `.env` 为 `MODEM_PCM_BAUD=115200` → 再启 Edge。

**已否定 / 已回退的调参**：

1. **全程 `tanh` 软限幅**：会压高频，加重「隔板」感 → 改为 **仅 peak>28000 才软限**。  
2. **强预加重（0.85）全量**：刺耳 → 现用高通 + 中等预加重（非全量 0.85）。  
3. **`write_timeout=0.15`**：静音，见 §2.2。  
4. **venv launcher + 子进程**：同一次启动的父子属正常；**两个独立 `app.py`** 才危险。

**推荐本机 `.env`（调试收敛值，可按听感微调用）**：

```env
MODEM_AUDIO_MODE=simcom_pcm
MODEM_PCM_PORT=COM6
MODEM_PCM_BAUD=115200
MODEM_TX_GAIN=0.91      # = 1.1 / 10^(1.63/20)，补偿预加重降档带来的 +1.63dB，见 §5.7
MODEM_AGC=false         # 真机 A/B 判定无可闻收益，关闭（§5.2）
MODEM_AGC_TARGET_DBFS=-23.4
QWEN_VOICE=loongmary
QWEN_REALTIME_MODEL=qwen-audio-3.0-realtime-plus
```

相关代码：

- 增益 / 清晰度 / 软限：`SerialPcmAudioBridge.amplify_for_modem`、`apply_phone_clarity`、`apply_soft_limit`  
- 24k→8k：`StreamingPcmDownsampler`（3.4kHz 低通）  
- 带宽钉 8k：`AT+CPCMBANDWIDTH=1,1` 后 **读回** `AT+CPCMBANDWIDTH?`（日志应出现「PCM 带宽已确认 8kHz」）

## 3. 快速诊断清单（下一通没声时）

按顺序看 `data/app.log` + 最新 `data/recordings/*-inbound-*/`：

0. **先看 `AT+CPCMREG=1` 用了几次**。出现 `尚未读回 mode=1` → 模组 USB Audio 端点退化，
   这通的音频不可信，别拿它调参（见 §5.3；耗时本身不是判据）。处置：串口还在就发
   `AT+CRESET` 等重新枚举；串口已消失（`CM_PROB_PHANTOM`）才需要彻底断电 10s。
   宿主 USB 软拔插和 `AT+CFUN=0/1` 都清不掉这个状态（见 §5.8）。
1. **有没有** `[下行·Agent]` / `首音频延迟`？  
   - 无 → 查 Realtime：`Unsupported voice` / `Cannot create response` / Key 401。  
   - 有 → 模型侧已出声，查 PCM。
2. **有没有**成片 `写入 NMEA PCM 超时`？  
   - 有且 `agent_queued` 长期 0 → COM6 / `write_timeout` / `CPCMREG` / 是否抢口。  
   - 无，且 `written≈16kB/s`、`agent_queued>0` → 链路在写，查增益与听感。
3. **`meta.json`**：`downlink_bytes`、`audio_out_bytes`；`downlink.wav` 的 peak / speech RMS。  
4. **带宽日志**：是否「PCM 带宽已确认 8kHz」。VoLTE 误走 16k 按 8k 解会极糊（见 `HANDOVER.md` / `_set_simcom_pcm_bandwidth`）。

## 5. 仍开放的问题

1. **主观清晰度 / 宽带**：8k 窄带听清≠高清。批次 [#119](https://github.com/tianye1999/callpilot/issues/119) / 分支 `feat/simcom-pcm-16k` 的静态 16k 已证伪（见 §5.1 归因），改由「实测字节率自适应」重做；当前靠 §5.2 的下行 AGC 拿听感。  
2. **偶发写超时**：成功通话末尾仍可能出现累计 1 次；成片超时（几十上百）仍要查抢口/波特率。  
3. **Windows 本机旁听**：未实现；电话侧听感仍要以真机为准。  
4. **与 `HANDOVER.md` P0 的关系**：macOS libusb 发送方向未在本轮解决；Windows 官方 COM 已证明可走通，勿用 libusb 结论否定 COM 路径。  
5. **开场白句中近静音**：`183256` downlink 内有多段 40–500ms 近静音（非全 0），部分「断续」来自 TTS 韵律/流式间隙，不只是 COM。

### 5.1 8k / 16k 切换（#119）

```env
MODEM_PCM_RATE=8000   # 默认窄带；written≈16KB/s；带宽日志 8kHz（本机推荐）
MODEM_PCM_RATE=16000  # 宽带实验；written≈32KB/s；带宽日志 16kHz；须整链一致
```

**2026-08-11 真机（联通来电 `094630`）16k 回归 —— 已归因**：

| 项 | 结果 |
|---|---|
| `AT+CPCMBANDWIDTH=0,0` 读回 | 「已确认 16kHz」 |
| 下行写统计 | `written≈160kB/5s`（= 32KB/s，按 16k 发） |
| 缓冲 | `buffered` 涨到 66560B 且不回落 |
| **上行实测** | `uplink_bytes=158400` / PCM 开启后约 10.2s ≈ **15.6KB/s** |
| `downlink.wav` | 16k、F0≈225Hz（我们发出去的没问题） |
| **听感** | **断续 + 异常厚重，原音色破坏** |

**根因：模组实际仍在 8k，我们却按 16k 发。** 上行 15.6KB/s = `8000×2B`，是硬证据；
`AT+CPCMBANDWIDTH?` 读回的是**设置值，不是实际协商的语音编解码**，空口没协商到
AMR-WB 时它照样回 16kHz。两个症状因此同源：

- **异常厚重** = 16k 采样的 PCM 被 8k 通路播出 → 半速 → 降一个八度；
- **断续** = 我们灌 32KB/s、模组只吃 16KB/s → 背压积压 → 丢帧。

**教训：`CPCMBANDWIDTH` 读回不可作为验收依据，必须用字节率实测。**
判据：上行 ≈16KB/s → 窄带；≈32KB/s → 宽带。

因此 #119 的正确形态不是「静态开 16k」，而是**通话开头按实测字节率判定、宽带才切 16k、
否则自动回落 8k**。在此之前本机保持 `MODEM_PCM_RATE=8000`。

切 16k 后若听成噪声（沙沙声）：AT 与软件率不一致。若厚重/降八度且 `buffered` 单调上涨：
就是本条——模组仍在 8k，不是 EQ 能救的。

### 5.2 下行 AGC（窄带听感的主要抓手）

16k 走不通后，不动硬件能拿到的主要增益不在带宽，而在**动态范围**：窄带里句尾、轻辅音
常掉到听阈以下，而静态 `MODEM_TX_GAIN` 只能在「削顶」和「听不清」之间二选一。

`PhoneAgc`（`audio_bridge.py`）按 ~5ms 子块跟踪 RMS，做标准下压式压缩：超过
`threshold`(默认 = target − 10dB) 的部分按 ratio(3:1) 压回来，再叠静态补偿增益
`makeup = target − threshold`，把整体抬到 `MODEM_AGC_TARGET_DBFS`。

**`threshold` 必须跟着 target 走，不能写死**：写死 −28 时，`MODEM_AGC_TARGET_DBFS`
在自己声明的量程(−40…−6)里有三分之一是完全失效的——target ≤ −28 时 `makeup` 恒为 0
（旋钮拧了没反应，日志还照报 target），target ≥ −12 时又被 `max_boost` 顶死。

**抬轻音必须靠 makeup，不能靠「慢释放慢慢爬」**——句尾辅音只有几十毫秒，等释放爬上来
早过去了。第一版就是这么写的，实测只压不抬（`speech_rms` 反而降 1.3dB），已改。

gate(−52dBFS) 以下**冻结**增益而非归零：既不主动继续抬底噪，也不会每个词头因增益从 0
重爬而削软起音。注意冻结≠不放大——冻住的增益照样作用在底噪上，能保证的只是「不随时长
继续爬」。块间对增益线性插值避免台阶/咔哒。每通新建实例，增益状态不跨通继承。

链路顺序：`apply_phone_clarity` → **AGC** → `MODEM_TX_GAIN` → `apply_soft_limit`。

**三个容易踩的实现坑**（2026-08-11 独立 review 抓出，均已修）：

1. **增益初值必须是 `makeup` 而不是 0dB**。稳态增益就是 `makeup`(+10dB)，从 0 起会被
   release 拖出约 500ms 渐强；而 `PhoneAgc` 是**每通新建**的，等于每通开场白都淡入
   （实测 0–100ms 段低 3.6dB）。
2. **AGC 内部不能硬削**。原实现结尾直接 `np.clip`，一旦削平，下游 `apply_soft_limit`
   只是把已失真的波形整体缩小，救不回来，而且 `peak` 指标上完全看不出来。现按块峰值算
   增益天花板（`PEAK_CEILING=0.99`）并**回扫一格**——块内插值是从上一块的增益爬到本块的，
   所以上一块也不得超过本块天花板，否则强音起头的前几个样本照样削（构造用例实测 23 个样本
   顶到负满幅）。
3. **`MODEM_AGC_TARGET_DBFS=nan` 会让整通下行变成数字静音**。`config.get_float` 只挡
   `ValueError`，而 NaN 穿得过 `min/max`（与 NaN 的比较恒为 False），一路变成 NaN 增益，
   `np.rint(nan)` 转 int16 得 0。已按 `AGENT_UPLINK_GAIN` 的既有写法加 `math.isfinite`。

**三通真机 downlink 离线回放**（先把当时的 `MODEM_TX_GAIN=1.35` 除回去还原 AGC 输入，
再按新链路重跑；`MODEM_TX_GAIN=1.0`）：

| 通话 | 旧链路 speech RMS / 动态跨度 / peak | AGC 后 |
|---|---|---|
| `185257` | −21.6dBFS / 18.9dB / 24962 | −20.1 / 15.9 / 22250 |
| `183256` | −19.2dBFS / 18.0dB / 27030 | −19.6 / 16.9 / 22363 |
| `182906` | −16.7dBFS / 21.1dB / 23990 | −18.8 / 20.0 / 21079 |

**通与通之间的响度散布从 4.9dB 收到 1.3dB**，峰值同时降了约 2500（多出的余量给限幅器），
削顶 0.000%。这才是 AGC 的主要收益——不是「更高清」，是**每通都稳、不用再按通调增益**。

> **2026-08-11 修正：上面这条「收窄通间散布」的收益不普遍成立。**用当天 5 通
> （`121544`/`111513`/`103536`/`100352`/`095958`）重跑，AGC 输入的通间跨度本来就只有
> **0.76dB**，开 AGC 后是 0.72~0.81dB —— **完全没有收窄**。8/10 那三通之所以散布 4.9dB，
> 是那批通话本身内容/配置不同；同一段开场白、同一 voice 的情况下 TTS 输出高度一致。
>
> 更要紧的是我一度把「`111513` 与 `121544` 差 1.8dB」当成通间漂移的证据向用户复述过，
> **那是错的**：两通的 AGC 输入完全相同（均 −22.47dBFS），1.8dB 全部来自我自己改的
> `MODEM_TX_GAIN`（1.35→1.1）。比较任何「通间差异」之前，先把链路上人为改过的增益除回去。
>
> 所以在本机这套链路上，AGC 的实际作用只剩**压动态范围**（62.9dB → 57.5dB）和
> 抬高峰值余量（20341 → 17127）。是否更好听只能真机试听，不能从指标推断。

注意 20ms 帧的 p10 基本没变（−33 → −30）：那些帧多是词间停顿和塞音闭塞段，压缩器既不能、
也不该把它们填平，填平了反而不自然。

**采样率不能 `from ... import MODEM_RATE`**：那是导入时按值拷贝的，`configure_modem_rate()`
改的是 `audio_bridge` 的全局，改不到拷贝（`call_agent` 曾因此在 16k 下把录音标成 8k、
TurnArbiter/DTMF 全按 8k 算）。已改为在用时取 `audio_bridge.MODEM_RATE`；`call_log` /
`web/server` 的函数内 import 是正确写法。**`remote_dialer.REMOTE_AUDIO_RATE` 与
`livekit_media` 的模块级常量仍是导入时快照，所以远程手机接管这条链目前只支持 8k**——
将来做 16k 自适应必须先改这两处，否则会静默半速。

同理，`SerialPcmAudioBridge` 的 `write_size` 默认值不能写 `= NMEA_WRITE_SIZE`：默认参数
在类定义时求值，16k 下每 100ms 只喂 8k 的字节数 → 永久欠载 → 电话侧断续。已改成
`None` 表示「构造时再取」。

```env
MODEM_AGC=false             # 本机真机 A/B 判定无可闻收益，见下面「最终判定」
MODEM_AGC_TARGET_DBFS=-23.4 # 拉齐的是 RMS 不是峰值；越大越响，钳在 [-40, -6]
```

开 AGC 后 `MODEM_TX_GAIN` 退化成纯微调；整体偏响/偏轻**优先调
`MODEM_AGC_TARGET_DBFS`**，别再把 `MODEM_TX_GAIN` 往上堆（会顶到限幅器）。

**最终判定（2026-08-11 真机 A/B）：本机链路上 AGC 无可闻收益，默认关闭。**

A/B 做了等响处理才有意义：直接开 AGC 会连响度一起变，听感分不清是「更清晰」还是
「更响」。先离线扫 target，找到能让 speech RMS 落回基线 −21.6dBFS 的值（−23.4），
再开 AGC 拨测，最终 `123213`(AGC 开) 对 `121544`(基线) 的 speech RMS 是
**−21.66 vs −21.65dBFS**，动态范围 59.7 vs 64.7dB。

用户实听结论：**「至少没变坏，听不出来有明显更清晰」**。也就是说那被压掉的 5dB 动态
在窄带电话上听不出来。代码与开关保留（`MODEM_AGC=true` 即可启用），但不默认开——
没有可闻收益的复杂度不该常驻在通话链路上。

这条也复核了 §5.2 开头「动态范围是不动硬件的主要抓手」那个判断：**方向错了**。
真正能被听出来的是频谱倾斜（§5.7），不是动态范围。

**真机逐帧 A/B（`185257` 无 AGC vs `103536` 开 AGC，同一句开场白、都是 264 帧）**：

| 帧类别（按 `185257` 定死） | 帧数 | 基准 | 开 AGC | Δ |
|---|---|---|---|---|
| 语音 (>−25dBFS) | 151 | −18.1 | −16.8 | **+1.3dB** |
| 拖尾 (−25~−50) | 47 | −33.1 | −29.7 | **+3.4dB** |
| 静音 (<−50dBFS) | 66 | −77.3 | −72.2 | **+5.0dB** |

逐帧增益抖动中位 0.33dB、p90 1.01dB。AGC 是**把弱的抬得更多**、反差变小，
不会把词尾压掉；−72dBFS 的静音帧仍在听阈之下，没有泵底噪。

**踩过的坑（指标假象）**：先用「落在 −60~−30dBFS 的帧的中位数」当缝隙电平，
得出「AGC 把缝隙压低 2.3dB、需要把 release 从 120ms 放慢到 200ms」的结论——
**是错的**。参数一变，落进那个区间的帧集合就跟着漂移，中位数量的不是同一批帧。
改成**用基准信号把帧集合定死、各参数下测同一批帧**后结论直接反转（release 越慢反差
越大，120ms 最好）。教训：比较类指标的分组必须由基准信号决定，不能由被测信号自己决定。

**已修的实现缺陷**：`PhoneAgc.process` 早期版本对尾块补零后直接 `np.mean` 求 RMS，
chunk 长度不是 5ms 块整数倍时电平被稀释 → 增益虚高，每个 chunk 边界抖一下。
现按真实样本数取平均（`counts[-1] -= pad`），并有单测钉住。

### 5.3 断续排查：先看 `CPCMREG` 重试次数，别信 `downlink.wav`

**`downlink.wav` 只记录「应用产出的音频」，不记录写线程补的静音，更不记录模组实际
吞吐的情况。**用它做逐帧对比可以证明「软件没多加缝隙」，但**不能**用来排除断续——
2026-08-11 就是这么误判的（拿录音断言「断续是 TTS 停顿、与配置无关」，用户实听反馈
「差异巨大」，复查通道建立日志才发现是模组）。

**真正的先导指标是通道建立耗时与 `AT+CPCMREG=1` 的重试次数**：

| | 好通话 `185257` | 断续通话 `103536` |
|---|---|---|
| `AT+CPCMREG=1` | **第 1 次成功**，1.2s | **第 1 次回读失败告警**，第 2 次成功，**7.2s** |
| 来电 → 音频桥就绪 | **3.24s** | **10.86s** |
| Edge 启动时的空闲探测 | 正常 | 同样 `尚未回读 mode=1` |

端点连注册都要重试的模组，收发 PCM 必然不稳 → 电话侧严重断续，而这**在录音里完全看不见**。
本次的诱因是当天的 16k 实验把端点搞进了退化态，但后来发现**正常通完一通就足以触发**。
处置见 §5.8：串口还在就发 `AT+CRESET`（2026-08-12 多次验证足够），串口已消失才需断电。

**判据（只能证伪，不能证真）**：日志里只要出现 `AT+CPCMREG=1 尚未回读 mode=1`
（无论第几次最终成功），这通的音频就不可信，别再拿它调增益/EQ/AGC——先断电重来。
**但反过来不成立**：同一天 `113347` 第 1 次注册就成功、来电→就绪 3.92s、写入满速率、
录音完好，用户那头却**全程静音**。所以它是必要条件，不是充分条件，不能当放行标准。

**耗时不是判据，重试次数才是**（2026-08-11 用全部 23 通复核）。曾把「来电→就绪 > 6s」
当退化标志，于是把 `121544` 判成退化——而那通用户实听是好的。按重试次数重排后无一例外：

| 通话 | `CPCMREG` | 来电→就绪 | 实听 |
|---|---|---|---|
| `121544` | 1 次 | **15.16s** | 好 |
| `123213` | 1 次 | 3.57s | 好 |
| `132201` | 1 次 | 2.86s | 好 |
| `124158` | **3 次** | 9.94s | **严重断续** |
| `131136` | **6 次** | 失败 | **建不起来** |

**一次注册成功的通话，哪怕慢到 15s 也是好的；需要重试的通话，哪怕最终成功也必坏。**
所以慢 ≠ 坏，别再用耗时当先导指标。

`downlink.wav` 和写入统计则连坏通话都排除不掉：`124158`（严重断续）与 `123213`（好听）
的首窗 `written` 都是 80320 bytes、峰值 `buffered` 都是 31040 bytes，**逐项相同**。

**结论：目前没有任何一个自动指标能替代真机试听。**`downlink.wav`、写入统计、建立总耗时
都被证伪过；`CPCMREG` 重试次数是目前唯一站得住的**证伪**指标，但仍不能证真——`113347`
第 1 次注册就成功、写入满速、录音完好，用户那头却全程静音（原因见 §5.6：模组重新枚举后
Edge 没重启）。

### 5.4 开场白自带的停顿（次要因素，非断续主因）

对 `103536` / `185257` 逐段扫静音（两通逐帧几乎一致，说明**与配置无关**）：

| 位置 | 时长 | |
|---|---|---|
| 0.00s | 100~120ms | 开头 |
| 0.74s | 260ms | 句中 |
| **2.48s** | **480~500ms** | **句中** |
| 4.46s | 180ms | 句中 |
| 5.02s | 260ms | 结尾 |

**两通的缝隙位置与时长几乎逐帧相同（±20ms）**：5.28s 的开场白里句中静音合计
**920~940ms，占 17~18%**，正中间还有一个近半秒的停顿。静音帧是模型生成的近零采样
（无全零断点），即 **TTS 韵律停顿**。

这部分与配置无关、改增益/EQ/AGC 都不会变，但**它在 8-10 号那些「可以了」的通话里
同样存在**，所以它不是 2026-08-11「断续严重」的原因（那次是 §5.3 的模组退化）。
真要减轻，两条路：把开场白改短（少几个分句边界），或在下行链路里把句中静音段压到
上限（如 ≥150ms 截到 150ms，只压句中不动首尾）。**先确认模组健康再谈这个。**

### 5.5 音量定档：`MODEM_TX_GAIN=1.1`（2026-08-11 真机确认）

模组恢复健康后重新按听感调音量，结果：

| 通话 | tx_gain | peak | speech RMS | hi/mid | 实听 |
|---|---|---|---|---|---|
| `111513` | 1.35 | −2.4dBFS | −19.9dBFS | 0.183 | 音量太高，略微刺耳 |
| `121544` | **1.1** | **−4.1dBFS** | **−21.6dBFS** | 0.183 | **合适** |

选 1.1 不是试出来的：`185257` 那通用户评价「可以了」，它的 speech RMS 正好是 −21.6dBFS，
而 `111513` 是 −19.9dBFS，差 1.8dB，`1.35 / 10^(1.8/20) ≈ 1.1`。一次到位。

注意 **hi/mid 两通完全相同（0.183）**：纯降增益不改音色。所以如果降完音量还嫌刺，
那刺来自 `apply_phone_clarity` 的预加重（8k 系数 0.65，当初为治「闷」提上去的），
要动的是那个系数而不是继续降增益——这两个旋钮别混着调。

也顺带说明了 AGC 的价值：`111513` 和 `185257` 配置完全相同，speech RMS 却差 1.8dB，
这个通间漂移正是 AGC 要收的。但 AGC **尚未做过真机 A/B**，目前默认关。

**A/B 时必须先把响度这个变量锁死**。默认 `target=-18` 配 `MODEM_TX_GAIN=1.1` 会让最终
电平到 −15dBFS 左右，比用户认可的 −21.6dBFS 高 6dB 多 —— 这时候听到的差异全是响度差异，
压缩本身的好坏一点都测不出来。用 `.cache/agc_target_sweep.py` 在真机录音上扫出等响点：

| target | 最终 speech RMS | 通间跨度 | 峰值 | 动态范围 |
|---|---|---|---|---|
| −18.0 | −18.14dBFS | 0.77dB | 24629 | 58.3dB |
| **−23.4** | **−21.66dBFS** | 0.74dB | 17127 | 57.5dB |
| −27.5 | −24.40dBFS | 0.80dB | 12995 | 56.6dB |
| 关闭 | −21.65dBFS | 0.76dB | 20341 | 62.9dB |

取 **−23.4**：与关 AGC 的基线响度重合（−21.66 vs −21.65），A/B 里只剩「动态压缩」一个变量。

注意 target 不等于输出电平。`threshold = target − 10`、`ratio = 3:1`、`makeup = 10dB`
推出的不动点是 **输入 = target + 5**（此时增益恰为 0dB）。要「响度不变」就令
`target = 输入电平 − 5`；本机 clarity 后的输入是 −22.47dBFS，故 −27.5 是增益 0 的点，
而叠上 `MODEM_TX_GAIN=1.1`（+0.83dB）后等响点前移到 −23.4。

### 5.6 模组不稳定时的恢复顺序（重连 ≠ 重启）

模组掉电/重新枚举后，Edge 的自动重连**只重连 AT 口（COM8）**，而 PCM 口（COM6）是随
模组重新枚举出来的。走这条路径的 `113347` 出现了「各项指标全绿但电话侧全程静音」。

**已验证能出声的顺序只有一个**：模组断电 10s → 上电等 COM 齐 → **再（重）启 Edge**。
即模组重上电后，Edge 必须跟着重启，不能依赖它自己重连。

**来电路径缺少端点复位（2026-08-11 改，尚未经真机验证）**：外呼在 ATD 前无条件发
`AT+CPCMREG=0,1` 清端点（`_prepare_simcom_for_dial`，注释：「不清理会导致 CPCMREG
始终无法进入 mode=1」），而来电路径的重试循环原本只是**反复重发 `=1`**——裸重发清不掉
端点里的半开状态。这能解释「来电侧反复重试、外呼侧没有」的不对称，但**它只是假设**：
定档那通 `132201` 第 1 次就注册成功，复位分支根本没走到，仍待下次出现重试时验证。

**复位必须分清两类失败**（第一版没分，独立 review 判为 high）：

| `_start_simcom_pcm_once` 的失败 | 含义 | 处置 |
|---|---|---|
| `=1` 回 ERROR（`accepted=False`） | 端点状态可疑 | **复位**再重试 |
| `=1` 回 OK 但 `AT+CPCMREG?` 还不是 mode=1（`accepted=True`） | 注册**正在异步进行** | **绝不复位** |

对第二种发 `=0,1` 会**打断一次本来就要成功的注册**，把「慢但正常」的模组推进多次重试
路径——而多次重试与实听断续强相关。真机确有整段建立慢到 15s 却仍第 1 次注册成功的模组
（`121544`）。所以 `_start_simcom_pcm_once` 改为返回 `_PcmStartResult(ok, accepted)`。

**而且整轮只复位一次**：复位每次多花一条 AT，模组繁忙时单条可达 3~4s，而窗口只有 12s
（`_SIMCOM_PCM_ENABLE_TIMEOUT`）。每轮都复位会把本该用于重试的预算烧光，让慢模组更容易
超时失败。两个回归锁分别钉住「该复位时复位」与「不该复位时绝不复位」，并做过突变验证
（去掉 `accepted` 判断、去掉复位、去掉「只复位一次」，三种改法都能让对应测试变红）。

补充两条排查手段：

- `Get-PnpDevice | Where FriendlyName -match SimTech` 看 `Status`：`CM_PROB_PHANTOM`
  表示模组已从 USB 上完全消失（只剩注册表残留），此时任何软件侧重试都没有意义。
- Windows 上 `app.py` **只能强制终止**（`taskkill` 不带 `/F` 会拒绝，提示只能用 `/F`）。
  也就是说「优雅退出」目前不是一个选项，除非给 `app.py` 加信号处理。曾一度怀疑强杀会把
  端点搞退化，但既然没有替代手段，这条假设无从验证，**不要**据此下结论。

**关于供电**：本机是纯 USB 供电（一根线到电脑）。SIM7600 在 LTE 发射瞬间的峰值电流
超出 USB 2.0 标准口的额定供给，是这类模组的已知风险点，与「必须断电才能恢复」的现象
也吻合。但**目前没有直接证据**（唯一一次「模组自己掉线」经核实是人为拔线），
先记录为待验证项，不作为结论。要验证的话，接一个带独立电源的 USB Hub 即可对照。

### 5.7 音色：预加重系数才是「刺耳 / 发闷」的旋钮

响度定档到用户认可的 −21.6dBFS 后仍反馈**「音量还是有点刺耳」**——同一电平下还嫌刺，
说明刺不来自响度，来自**频谱倾斜**。

`apply_phone_clarity` 的等效响应是 `H(z) = 1 - 0.58*pre_coef * z^-1`。**用「3.4kHz 相对
300Hz 抬了多少 dB」来记这个旋钮，比记系数直观**：

| `pre_coef` | 倾斜 | 录音实测 hi/mid |
|---|---|---|
| 0.65 | 6.47dB | 0.183 — 真机实听刺耳 |
| 0.50 | 4.88dB | 0.138 |
| **0.35** | **3.37dB** | **0.105** — 当前值 |
| 0.20 | 1.90dB | 0.081 — 已低于单测要求的 +25%，再降等于没做 |

0.65 是 2026-08-10 晚为治「闷」提上去的，而**那晚的「闷」与断续同源**（模组端点退化，
见 §5.3）——根因不在音频处理上，却按音频处理去补偿了，模组恢复后自然显得过亮。
教训与 §5.3 同：模组状态存疑时，不要用听感去标定软件参数。

**改这个系数必须同步补 `MODEM_TX_GAIN`**：预加重的低频衰减跟着系数变，0.65→0.35 会让
总电平涨 **1.63dB**。不补的话音色和响度两个变量一起动，用户反馈归因不了——所以
`MODEM_TX_GAIN` 同时从 1.1 降到 `1.1/10^(1.63/20) = 0.91`。离线核过：新旧两套参数的
speech RMS 是 −21.55 vs −21.65dBFS（等响），高频相对低频降 2.4dB，peak 20341 → 17874。

再调的话按二分走：还嫌刺就往 0.2 靠，变闷就退回 0.5，**每次都要重算 `MODEM_TX_GAIN`**。
`.cache/preemph_sweep.py` 可以直接在既有录音上换系数看倾斜，不用真机试错。

这个耦合也波及**默认值**：`pre_coef` 是写死在代码里的，所有部署都受影响，所以
`MODEM_TX_GAIN` 的注册表默认与 `.env.example` 一并从 `1.0` 改到 **`0.83`**
（= `1.0 / 10^(1.63/20)`），否则默认部署会凭空响 1.63dB（独立 review 判为 medium）。
`test_tx_gain_default_compensates_clarity_preemphasis` 钉住这个关系。
注意 0.83 **不是「中性」值**——它是补偿量，别当成"不改变音频"的默认。

顺带：`MODEM_AGC` 的默认也由 `true` 改为 `false`（§5.2 的等响 A/B 结论）。

**真机确认（2026-08-11 13:22，`132201`）：用户实听「不刺耳了」。**三通录音把变量隔离得很干净：

| 通话 | speech RMS | 倾斜(2–3.4k 减 0.3–2k) | 削顶 | 实听 |
|---|---|---|---|---|
| `121544` pre=0.65 g=1.10 | −21.65dB | −7.37dB | 0% | 刺耳 |
| `123213` 同上 + AGC | −21.66dB | −7.01dB | 0% | 仍刺耳 |
| `132201` pre=0.35 g=0.91 | −21.55dB | **−9.78dB** | 0% | **不刺耳** |

三通响度跨度仅 0.11dB，唯一变量是倾斜 → **刺耳由频谱倾斜决定，与响度、动态范围无关**。
`123213` 那通尤其能说明问题：AGC 把动态范围压了 5dB 而倾斜几乎没动，听感照旧刺。

真机实测值与 `.cache/verify_equal_loudness.py` 的离线预测逐项吻合（−21.55dB / peak 17874 /
−9.78dB），说明这条链路上**音色可以离线定值，不必真机试错**——真机只需最后确认一次。

### 5.8 跨通端点劣化：三种复位手段的对照（2026-08-12，#121）

端点劣化不需要 16k 实验这种诱因，**正常通完一通就会发生**：第 1 通好，第 2 通起
`AT+CPCMREG=1` 首拒、听感断续，严重时整通无声。当天连拨即可稳定复现。

三种复位手段做过同条件对照，判据统一为「下一通 `AT+CPCMREG=1` 是否第 1 次就进 mode=1」：

| 手段 | 恢复耗时 | 是否重启 USB | 下一通 |
|---|---|---|---|
| 宿主 USB 软拔插（`Disable/Enable-PnpDevice`） | ~10s | 否（只重置 Windows 那一端） | **首拒 → 断续/无声** |
| `AT+CFUN=0` → `AT+CFUN=1` | **2s**（`+CREG` 起算） | 否（COM 口全程不消失） | **首拒 → 断续** |
| `AT+CRESET` | 14~20s（USB 重新枚举） | 是 | **第 1 次进 mode=1，正常** |

**规律很干净：不让 USB 重新枚举，就清不掉端点状态。**软拔插和 `AT+CFUN` 快，恰恰是
因为它们没碰 USB —— 而问题就在 USB 这一层。`AT+CFUN=0/1` 是标准 3GPP 指令，能治
「SIM 卡住、必须插拔 SIM」那一类故障，但它与 USB Audio 端点半死是两回事，别混用。

落地为 `MODEM_RESET_AFTER_HANGUP`（默认开）：正常通完一通后发 `AT+CRESET` 并等重新
枚举，代价是重启期间约 15-20s 收不到来电。`MODEM_USB_SOFT_CYCLE_AFTER_HANGUP` 默认关，
仅留作回退排查。

**收尾只能有一条恢复路径**。真机 15:58 踩过：`_shutdown_agent` 走完模组重启后，
`_run` 的 finally 里那个旧软拔插调用点仍在跑，于是重启完成 13s 后又把 USB 拔了一次，
白等且再次撕断 AT 口。模组重启成功时必须同时把软拔插标记为已完成。

**顺带证伪一条判据**：`timeouts=0` 与 `written` 满速**不代表链路健康**。`AT+CFUN` 那轮
的第 2 通 `written=81600/80000`、`timeouts=0`、`write_ms_p95=0.78ms`，实听却是断续的 ——
劣化轻时数据写得出去、听感已经坏了。这与 §5.3 结论一致：**`CPCMREG` 重试次数是唯一
站得住的证伪指标**，写入统计只能捕捉更严重的那一档（整通无声）。

**同时修正 §5.3 / §2.2 的旧处置**：那里写「`AT+CRESET` 与重启程序都不够，必须彻底断电
10s」。当天多次验证 `AT+CRESET` 足以恢复（手动与自动链路各若干次，均为下一通首次进
mode=1）。旧结论的场景是模组已 `CM_PROB_PHANTOM`（从 USB 上彻底消失），那种情况下
AT 口都没了、`AT+CRESET` 自然发不出去 —— **先看串口还在不在，再决定断电还是 `CRESET`**。

## 6. 建议验收口令（交付前）

0. **真机试听是唯一的放行标准**，下面的日志项只能用来排除坏通话（见 §5.3 结论）。  
1. 重启 Edge → 日志「模组已连接」+ `/api/meta` `credentials.ok`。  
2. 手机打模组号 → 听到开场白，字句可辨、无明显破音。  
3. 日志：`PCM 带宽已确认` 与 `MODEM_PCM_RATE` 一致（8 或 16kHz），`tx_gain` 符合 `.env`，无成片写超时；16k 时 `written≈160000 bytes/5s`。  
4. `downlink.wav`：有能量；`sample_rate` 写入 meta；clip ≪ 0.1%；增益按听感微调 `MODEM_TX_GAIN`。  
5. 日志出现「下行 AGC: 关闭」（默认；真机 A/B 判定无收益，见 §5.2）。若要重开，
   A/B **必须先等响**，否则听感分不清「更清晰」和「更响」。  
5b. 音色偏刺/偏闷调 `apply_phone_clarity` 的 `pre_coef`（§5.7），**并同步补
   `MODEM_TX_GAIN` 保持等响**，别用音量去掩盖音色问题。  
6. 若在验证 16k：**以上行字节率为准**（≈16KB/s 即模组仍在窄带，立即回 8k），不要只看
   `PCM 带宽已确认`。
